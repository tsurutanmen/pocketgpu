# 案 3「MEM_WRITE の思い込みの待ちをなくす」の設計（2026-10-10）

印：**[事実]** はソースで確かめたこと。**[推測]** は私の推論。
読んだのは `app\vk\icd\icd.c`・`app\vk\remote\server.c`・`app\vk\remote\proto.h`・`work\perf\report.md`・`app\vk\tools\slow_link.py` だけ。書き換えていない。行番号は 2026-10-10 15 時台に読んだ時点の物。

## 0. 要点

- [事実] ドライバは、メモリごとに「GPU が使う範囲と、それを使う submit の番号」の帳簿を持つ（`mu_note`・`mu_upto`）。MEM_WRITE には、書く範囲を使う最後の submit の番号（upto）を付ける。受け手はそこまでだけ待つ。
- [事実] ところが帳簿は、重なる・隣り合う範囲を 1 つにまとめ、番号は大きい方を取る。64 を超えると、メモリ全体を 1 つの範囲にまとめる。→ 書く範囲を使っていない新しい submit まで待つことになる（report.md の「思い込みの待ち」）。
- [事実] 帳簿から終わった範囲は消えない。ただし、受け手は upto を「まだ走っている仕事」とだけ比べるので、古い番号は待ちを生まない。[推測] 害になるのは「まとめるときに大きい番号を取る」ことのほう。
- 段取り：先に「待ちを全部外した版で、試験が壊れを拾えるか」を確かめる（M1）。そのあと、帳簿を「重ならない区間と、区間ごとの正しい番号」にする（M2）。約束事は変えない。

## 1. 今の作り

### ドライバ（icd.c）

| 場所 | 行 | 何をするか |
|---|---|---|
| `struct mem` の `use`・`nuse`・`cuse` | 987〜1002 | メモリごとの帳簿（`struct muse { off, end, msg }` の並び） |
| `mu_note` | 1007〜1038 | 範囲と番号を足す。重なる・**隣り合う**範囲があれば広げて 1 つにし、番号は大きい方。並びが 64 を超えたら、全部を 1 つ（全体の範囲・いちばん大きい番号）にする |
| `mu_upto` | 1041〜1048 | 範囲に重なる帳簿の番号のうち、いちばん大きい物を返す（線形に探す） |
| `memw_upto_on` | 1050〜1055 付近 | `IPHONE_VK_MEMW_UPTO=0` なら upto を付けない（受け手は、そのメモリを使う仕事を全部待つ） |
| `send_write` | 1822〜1829 | MEM_WRITE を積む。末尾に upto |
| `send_dirty` の中 | 1901 行付近 | 同じく MEM_WRITE に upto |
| `queue_submit` の中 | 8079〜8081 | submit を送った**あと**、その submit の記録が読む範囲（`rd`）と書く範囲（`r`）を、その submit の番号で `mu_note` する |
| メモリを放す所 | 2913 | 帳簿を空にする |

- [事実] `queue_submit` は、submit を送る前に、GPU が読む範囲のうちアプリが書いたページを MEM_WRITE で送る（`send_dirty`、7941〜7954 行）。この時点では、今の submit はまだ帳簿に載っていない。→ upto は「前の submit たち」だけを見る。今の submit より先に MEM_WRITE が受け手で処理されるので、これで正しい。

### 受け手（server.c）

- [事実] `case VR_MEM_WRITE`（2952 行〜）：`k = last_with_mem(mid)`（そのメモリを使う最後の仕事の位置）。末尾に upto があれば、`u` ＝ 一覧で番号が upto 以下の最後の位置。`k = min(k, u)` まで `drain_upto(k)` で待つ。
- [事実] upto がどの走っている仕事より古ければ `u = -1` で、待たない。

### 思い込みの待ちが起きる形（推測）

1. 隣り合うだけでまとめる：submit 100 が [0, 64KB) を読み、submit 500 が [64KB, 128KB) を読む。帳簿は [0, 128KB) 番号 500 の 1 つになる。アプリが [0, 4KB) を書くと、upto は 500 で、関係の無い submit 500 まで待つ。
2. 64 を超えてまとめる：DXVK のように 1 つの大きなメモリをたくさんの buffer で分けて使うと、すぐ 64 を超えて「全体・最新の番号」になる。どこを書いても最新の submit まで待つ。
3. report.md の「大きな塊全体が使用中に見える」はこの 2 つ。

## 2. 段取り

### M0：先に測る（直さない）

- ドライバ：`mu_note` で 64 を超えてまとめた回数、`nuse` の最大、`mu_note` に来る範囲の大きさの分布、MEM_WRITE の upto と「その時点の最新の submit の番号」の差。`IPHONE_VK_STATS=1` のときだけ数える。
- 受け手：MEM_WRITE（命令の番号 13）の GPU 待ちの回数と ms。今の `wait_by_op` で数えられる（64 未満）。
- 分かること：思い込みの待ちが本当にどれだけあるか。M2 で区間の数がどれくらいになるか（M2 のやり方を選ぶ材料）。

### M1：待ちを全部外した版で、試験が壊れを拾えるかを先に確かめる

- やり方
  1. 調べ用の切り替えを足す。受け手 `VKR_MEMW_NOWAIT=1` なら、MEM_WRITE の前の `drain_upto` をしない。
  2. 壊れを拾うはずの試験を、今の版と NOWAIT 版の両方で回す。**NOWAIT 版で落ちる試験だけを、M2 の確かめに使う**。落ちない試験は、この壊れを拾えない。
- 試験の候補（[推測] どれが拾うかは M1 で決まる）
  - 専用の小さな試験（作るかは向こうで決める）：CPU から見えるメモリの同じ場所に、毎回違う数字を書く → GPU でその場所を別の buffer に写す submit を出す → fence を待つ（ドライバはすぐ「終わった」と答える）→ 次の数字を書く、を繰り返し、最後に写した先を全部読み戻して、数字が順に並んでいるかを見る。NOWAIT 版なら、GPU が写す前に次の数字で上書きされて、数字が飛ぶはず。
  - CTS の `dEQP-VK.synchronization.op.single_queue.*`（host から書く・読む物）、`dEQP-VK.memory.mapping.*`、`dEQP-VK.api.copy_and_blit.*`（ステージングを使い回す物）。
  - 実際のアプリ：受け手のコメントに出てくる whisper・llama.cpp（計算でステージングを使い回す）。
- 戻し方：調べ用の切り替えなので、既定は今のまま。

### M2：帳簿を「重ならない区間と、区間ごとの正しい番号」にする（ドライバだけ）

- やり方（区間の表）
  1. 帳簿を、off で並べた重ならない区間の並びにする。`mu_note` は、新しい範囲と重なる区間を切り分け、重なった部分だけ番号を大きい方にする。重ならない部分は元の番号のまま。**隣り合うだけの区間は、番号が同じときだけまとめる**。
  2. `mu_upto` は、並びを二分探索して、範囲に重なる区間の番号の最大を返す。
  3. 区間が多すぎるとき（例 256 を超える）は、まず終わった番号（`g_done_msg` 以下）の区間を消す。それでも多ければ、隣どうしで番号の近い 2 つをまとめる（大きい方の番号を取る）。今の「全体を 1 つ」より狭い範囲で済む。
- もう 1 つのやり方（ページの表）
  - ページ（今の `PAGE`）ごとに番号を 1 つ持つ。正確で簡単。
  - [推測] ただし `mu_note` の手間が範囲の大きさに比例する。DXVK は大きな buffer の広い範囲を使うことがあり、256 MB の範囲なら 1 回で 65,536 ページを書く。1 コマに何十回もあると重い。M0 で範囲の大きさを測ってから選ぶ。
- 直す関数：`mu_note`・`mu_upto`・`struct mem`（帳簿の形）・メモリを放す所（2913 行）。
- 約束事：変えない。upto の意味（その範囲を使う最後の submit の番号）は同じ。受け手も変えない。
- 守ること
  - **upto は小さくしない**：その範囲を読む・書く、まだ終わっていないかもしれない submit の番号のうち、最大以上にする。小さいと、GPU が読む前に上書きして壊れる。区間を切り分けるとき、重なった部分は必ず大きい方の番号を取る。
  - **読む範囲と書く範囲の両方を載せる**（今どおり `rd` と `r`）。
  - **今の submit を載せる時期**：今どおり submit を送ったあと。送る前の MEM_WRITE は前の submit だけを見る。
  - **錠**：`g_muse_lock` で守る（今どおり）。
- 確かめ方：M1 で選んだ試験。M0 の数で、受け手の MEM_WRITE の待ちが減ったか。代役の Heaven で速さ（report.md の見積もりは +2〜3 コマ）。
- 戻し方：環境変数（例 `IPHONE_VK_MEMW_EXACT=0`）で今の `mu_note` に戻す。
- 難しさ：中。[推測] 危ないのは区間の切り分けの書き間違い。小さな単体の試験（範囲と番号を入れて、upto を確かめる）を先に作るとよい。

### M3：終わった区間を消す（M2 の続き）

- やり方：`mu_note` と `mu_upto` のついでに、番号が `g_done_msg` 以下の区間を消す。
- 前提：`g_done_msg` が新しいこと。今は REAL_FENCE のときだけ進む。`pipeline_lock.md` の P3（返事に終わった番号を付ける）が入ると、いつも新しくなる。[推測]
- 効き目：区間の数が増えすぎない。upto の値は変わらない（終わった番号は、受け手でも待ちを生まないので）。
- 戻し方：M2 と同じ切り替え。

### M4：受け手の `last_with_mem` を速くする

- [事実] `last_with_mem`（server.c 931 行〜）は、走っている仕事 × 記録 × 記録を探す `cbi()`（全部の記録を前から探す）× メモリの一覧、を線形に探す。
- やり方：`descriptor_tracking.md` の D2 と同じ形で、メモリごとに「最後に使った submit の番号」を submit のときに書いておく。
- 直す関数：受け手の `case VR_QUEUE_SUBMIT`・`last_with_mem`。

## 4. 見つけたこと（範囲の外）

- [推測] 受け手は、set を結んだ時点の set の中身（buffer の一覧）を、その記録の「使うメモリ」に足している（server.c 1281〜1283 行）。記録のあとで set を書き換える形（UPDATE_AFTER_BIND。vkd3d-proton の descriptor heap はこれを多く使う）だと、記録の「使うメモリ」が古いままになり、MEM_WRITE や MEM_READ の待ちが足りない恐れがある。今回の範囲ではないので、確かめていない。
